# CI/CD and delivery-path audit (2026-10-28)

Sources: `.github/workflows/ci.yml`, `.github/workflows/database.yml`, `docs/CI_CD.md`, the Database workflow run history on `main`, GitHub branch-protection API, and the previous release (PRs #162 / #163, `docs/releases/release-readiness-2026-10/`). The workflow files are unchanged by this release (no `.github` change in the delta).

## What runs when

| Trigger                                          | Workflow / job                                                                                                                                                                                                |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PR to **any** base (incl. `development → main`)  | `CI / application` (local-path guard, format, lint, typecheck, Vitest, build, `.next` scan for the PROD ref) and `CI / browser-smoke` (`--project=desktop`)                                                   |
| PR touching `supabase/**` (true for the release) | `Database / migrations-and-policies`: `supabase start` → `db reset` (all 54 migrations on a clean database) → `supabase test db` (pgTAP), via the ghcr.io-first registry wrapper                              |
| PR (Vercel integration)                          | Vercel **Preview** deployment (DEV Supabase); `Vercel Preview Comments`                                                                                                                                       |
| Push to `main`                                   | `CI / application`; `Database` (path-gated on `supabase/migrations/**` → true) runs **`deploy-migrations`** only (`migrations-and-policies` skipped on push); **Vercel Production deploy** starts in parallel |

Expected release-PR checks: `application`, `browser-smoke`, `Database / migrations-and-policies`, `Vercel`, `Vercel Preview Comments`. Known flake class: container-registry pull limits in `Database` (handled by the wrapper's bounded pull retries; SQL/pgTAP failures are never retried) and `browser-smoke` job timeouts on a slow runner (one T-5 occurrence, passed on re-run).

## Answers

| Question                                                    | Answer (evidence)                                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| When are PROD migrations applied by automation?             | Only by `deploy-migrations` on a push to `main` (`supabase link` + `supabase db push`, `environment: production`). **It is not working:** the latest run (`d08eb4e`, 2026-10-26) and every earlier `main` push failed at **`supabase link`** (authorization, #111). `db push` never ran |
| When does Vercel deploy Production?                         | On any push to `main` through the Git integration, in parallel with the workflows above. `main` has **no branch protection** (GitHub API: 404), so no check gates the deploy                                                                                                            |
| Can the frontend deploy before the required schema?         | **Yes.** Nothing orders Vercel after the migration job, and the migration job cannot currently succeed (#111, #113 open). The new app on the old schema fails                                                                                                                           |
| Are migrations guaranteed before application code?          | **No** by automation. They are guaranteed only by the **migrations-first manual procedure**                                                                                                                                                                                             |
| Can the migration workflow fail while Vercel still deploys? | **Yes** — exactly what happened on 2026-10-26 (deploy-migrations red, Production READY). With migrations applied first, that red run is a harmless no-op; if #111 were repaired, `db push` would find nothing to apply                                                                  |
| Rollback / recovery?                                        | See `RELEASE_PLAN.md`: Vercel promote of the previous Production deployment (old app is compatible with the new schema) + forward corrective migrations. No destructive schema rollback                                                                                                 |
