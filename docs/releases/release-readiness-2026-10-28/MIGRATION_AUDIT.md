## Findings

- **Destructive migration: NONE.** The only `DROP` is the old `private.tasks_notify` overload, replaced atomically in the same transaction; it is a private function reached only from other database functions. `revoke`/`grant` statements only _narrow_ (`revoke … from public, anon[, authenticated]`) or grant `execute` to `authenticated` on RPCs that check membership/role inside.
- **Existing PROD data is touched by exactly one statement:** the nullable `payload` column on `task_notifications` (metadata-only add). Everything else is new tables or function replacement, so there is no constraint or index that can fail on real PROD rows. (Contrast with the previous release, which needed data pre-flights.)
- **Order is internally valid** and follows version order: #11 (gate) → #12 (enum) → #13 (engine); inventory objects #2 → #3 → #4/#5/#6 → #7/#8 → #9 → #10. `supabase db push` / version-ordered apply is correct; no out-of-order or skipped version exists on PROD.
- **Transaction rule for a manual apply:** run #12 and #13 in **separate transactions** (PostgreSQL cannot use a newly added enum value in the transaction that adds it). One `begin; … commit;` per migration (the proven route) satisfies this.
- **Backward compatibility with the currently deployed app (`main@d08eb4e`): PASS.** New schema + old app works (see GO_NO_GO). **New app on old schema fails**, so migrations must precede the merge.
- **Reversibility:** forward-only. Recovery is a forward corrective migration restoring the earlier function body from git (`20261026120000` for `board_assign`, `20261025…` for `tasks_notify`); new tables/columns/enum value are left in place (harmless to the old app). Dropping them is never part of recovery.
- **Advisors:** PROD security advisors should show only the expected `authenticated_security_definer_function_executable` class; re-run `get_advisors` after applying (operator step, `RELEASE_PLAN.md`).
