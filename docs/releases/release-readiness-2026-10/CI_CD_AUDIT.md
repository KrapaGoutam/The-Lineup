# CI/CD audit

Sources: `.github/workflows/ci.yml`, `.github/workflows/database.yml` (on `development`), `docs/CI_CD.md`, GitHub API (branch protection, environments, secret names, run history), Vercel project settings. Nothing was triggered.

## Architecture as built

| Stage                           | Trigger               | What runs                                                                                                                                                                                                                                                                                                                   |
| ------------------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Feature / fix / docs branch     | PR into `development` | `CI`: `application` (format, lint, typecheck, Vitest, build, PROD-ref scan of `.next`) and `browser-smoke` (demo Playwright, desktop); `Database / migrations-and-policies` when `supabase/**` or `package*.json` change (local `supabase start` + `db reset` + pgTAP through the registry-mirror wrapper); Vercel Preview. |
| `development`                   | push                  | **No GitHub workflow** (CI triggers are `pull_request` and `push: main` only). Vercel builds a Preview (SSO-protected) pointing at DEV Supabase. The cumulative `development` head therefore has no CI run of its own.                                                                                                      |
| Release PR `development → main` | PR into `main`        | Same `CI` + `Database` checks on the exact head, plus Vercel Preview.                                                                                                                                                                                                                                                       |
| `main`                          | push                  | `CI` (`application`, `browser-smoke`); `Database / deploy-migrations` **if** the push touches `supabase/migrations/**` or the workflow file; Vercel **Production** deployment via Git integration.                                                                                                                          |

## Exactly what causes Production migrations to run

`Database / deploy-migrations` has `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`, `environment: production`, and runs `supabase link --project-ref $SUPABASE_PROJECT_ID` then `supabase db push` with the `SUPABASE_ACCESS_TOKEN` secret. It starts only on a **push to `main` that changes `supabase/migrations/**`or`database.yml`**. It cannot start from a feature branch, from `development`, from a Preview, from a PR (PRs get `migrations-and-policies`only), or from`workflow_dispatch`(the manual run executes only`migrations-and-policies`, which is gated `event_name != 'push'`). Secrets exist at repository level: `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_ID`.

The development→main merge **will** trigger it (it touches `supabase/migrations/**`).

## Findings

| #    | Severity                 | Finding                                                                                                                                                                                                                                                                                                                                        |
| ---- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CI-1 | **Blocker**              | `deploy-migrations` failed on the last 4 pushes to `main` (merges of PR #39 → 2026-09-11, #46, #47, #50 → 2026-09-20), preceded by 4 successes (2026-09-06..09). Documented cause: token cannot access the project (#111). There is no evidence since that the secret was repaired.                                                            |
| CI-2 | **Blocker**              | Even with a working token, `supabase db push` will not apply the 8 release migrations while `20260911130000` is missing from PROD history (out-of-order; needs `--include-all`) — #161. Expected CLI behaviour; not confirmed with a dry run because a dry run needs an authorised link to PROD, which this audit deliberately did not create. |
| CI-3 | **Blocker (procedural)** | No ordering between the Vercel Production deploy and `deploy-migrations` (#113). Merging triggers both at once. The release therefore must apply migrations **before** the merge (safe: old app works on the new schema, see `RELEASE_PLAN.md`).                                                                                               |
| CI-4 | Hardening                | `main` and `development` have no branch protection and there are no rulesets: checks are not required, direct pushes are possible. The `production` environment has no required reviewers, so `deploy-migrations` would run unattended on any `main` push.                                                                                     |
| CI-5 | Info                     | The `CI` workflow runs on `push: main` after merge, not before; with CI-4 it is advisory unless the release operator makes the release PR's checks green first (condition C6).                                                                                                                                                                 |
| CI-6 | Info                     | `deploy-migrations` is never exercised by PR CI (always skipped) — its health can only be proven by a real `main` push or a manual dry run from an authorised context.                                                                                                                                                                         |
| CI-7 | Good                     | Non-production builds are scanned for the PROD ref (`check-nonprod-env.mjs --scan .next` in `application`); local `npm run check:env` passes on `.env.development.local` and fails on `.env.production.local` as intended (names only, no values).                                                                                             |
| CI-8 | Good                     | The Database job retries only classified registry/network pull failures; SQL/pgTAP failures are never retried or skipped.                                                                                                                                                                                                                      |
