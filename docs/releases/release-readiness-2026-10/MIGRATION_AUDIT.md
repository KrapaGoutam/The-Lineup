## Append-only check (§7)

`git diff --diff-filter=M origin/main...origin/development -- supabase/migrations` → no migration that exists on `main` is modified; all 8 are additions relative to `main`. Within `development`, six files have one commit. **Two have two commits and one is a genuine in-place edit of a migration already applied to DEV:**

- `20261023100000_table_rotation_v2_session_integrity.sql` and `20261023110000_table_rotation_v2_trusted_mutations.sql` were created in `83b8b5c` (2026-10-23) and applied to DEV, then **edited in place in `96ee4af` (2026-10-24 00:53 CDT)** after an independent migration review ("both migrations are still unreleased (DEV only), so they are corrected in place" — commit message). Changes: (M1) disable/enable the occupancy trigger around the `service_session_id` backfill and an informational stale-duplicate notice in the pre-flight; (M2) three function-body fixes — `board_undo` orders by `id` only, `board_end_and_assign` rejects an inactive column, `get_or_create_active_session` raises instead of returning NULL.
- This breaches the append-only rule once. **Reconciliation performed in this audit (read-only):** on DEV, `public.board_undo` contains `order by id desc` and not the old `created_at desc, id desc`; `private.get_or_create_active_session` contains the new `closed session already exists` guard; trigger `table_rotation_entries_sync_occupancy` is enabled (`O`). The M1 edit only affects the one-time backfill (DEV's backfill already ran; DEV data and schema are unaffected). `board_end_and_assign` has since been re-created by the later migrations, so the M2 `active column` guard is covered by `20261026090000`/`20261026120000`. PROD never applied either file, so PROD will receive the final text; the deviation cannot cause PROD drift.
- Verdict: **reconciled, accepted deviation — not a blocker.** The pgTAP full-reset on every PR proves the final _files_ reproduce the schema, and the hosted suites ran against DEV after the edit. Recommendation: no further in-place edits to any migration once it has been applied to DEV; ship a new forward migration instead. (Supabase stores statements, not file hashes, so DEV cannot be hash-compared against the files.)
