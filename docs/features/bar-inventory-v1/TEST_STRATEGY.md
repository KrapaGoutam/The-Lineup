# Bar Inventory V1 — Test strategy

Layers mirror Tasks V1 and Table Allocation (audited): **U** domain unit (Vitest, colocated in `src/features/bar-inventory/domain`) · **C** component/hook (Vitest + Testing Library) · **P** pgTAP (`supabase/tests/database/NNNN_bar_inventory_*.test.sql`; next free number **0033**) · **R** hosted DEV DB through PostgREST with real JWTs (`tests/real/bar-inventory-*.db.real.test.ts`) · **E** demo Playwright (`tests/e2e/bar-inventory.spec.ts`, 3 projects) · **H** hosted DEV UI on a production build (`tests/real/ui/bar-inventory.real.spec.ts`). A scenario matrix file (`docs/features/bar-inventory-v1/TEST_MATRIX.md`, created in BI-0) maps IDs `BI-<area>-nnn` to layers and ACs.

## 1. Principles

- Business rules live in **pure domain functions** and, where the database must also know them (status, effective warning, suggested order, keys), in **one SQL function/view** — both proven against the **same golden vectors** (a JSON fixture consumed by Vitest and by a pgTAP generator) so they cannot drift.
- The database is the authority; UI tests assert what the server answered. Stale/concurrent behaviour is tested with real JWTs, not mocks.
- Parameterized scenario matrices (as in the Table Allocation cross-view matrix) instead of copy-pasted suites. Every table-like view runs the same filter/sort scenarios.
- Hosted suites build their own synthetic organization and clean up (existing harness); never PROD.

## 3. Golden vectors (shared)

`tests/fixtures/bar-inventory/status-vectors.json`: tuples `(on_hand, backup, cutoff, warning, par, archived) → (total, effective_warning, status, suggested_order)`. Seed rows: the worked example (2, 1, 4, 6, 12 → 3, 6, critical, 9); boundary totals `cutoff`, `cutoff+0.01`, `warning`, `warning+0.01`; `cutoff` null; `warning` null with cutoff 4 → 5 and cutoff 20 → 25; par null → "order needed"; par below total → 0; decimals (0.5 keg); archived excluded. Likewise `keys-vectors.json` (vendor/size/SKU keys) and the analytics vectors.

## 4. Test data and cleanup

Hosted harness fixtures extend `tests/real/support/harness.ts` (`Inventory` helper class like `Board`). Synthetic data only; teardown deletes ledger/stock/products/vendors **before** the generic membership teardown (append-only tables clear only by cascade — the same lesson as Tasks, see tooling notes).

## 5. Quality gate per phase

`npm run format:check`, `eslint --max-warnings=0`, `tsc`, `vitest run`, pgTAP (`supabase test db`, locally or CI), demo Playwright (3 projects), hosted DB suite after the DEV migration, hosted UI suite on a DEV-pinned production build (grep `.next` for the PROD ref = 0 files). Release adds the standard migrations-first checklist.

## 6. Out of scope for tests in V1

Load testing beyond the 5,000-row import and 5,000-product catalog; visual regression; real vendor integrations (none exist).
