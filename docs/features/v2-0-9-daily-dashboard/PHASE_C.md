Date 2026-11-19. Code under test: `development` `b3cedd8c` (V2.0.8 `94f05eb9` + V2.0.9 PR #359). Hosted DEV `opmujepkemwcdxxorhfd`, migration ledger 100 (head `20261119120000`), module enforcement `staged`. **No database change, no Production or `main` contact.**

## Method

One real-mode Playwright spec (`tests/real/ui/group2-phase-c.real.spec.ts`, fixture `tests/real/support/phase-c-fixture.ts`) against a dev server pinned to DEV (Neon blanked).

- A disposable synthetic organization (plus a second organization for the boundary check) is created and removed per run. No existing DEV row is read or changed.
- Truth values are computed from the RAW tables with the service role, independent of the application code.
- Tips mutations go through the same RPCs the Tips actions call, as the manager's real JWT. The browser is signed in with a real Supabase session cookie (the method of `single-context-auto.real.spec.ts`), then drives the Dashboard through the real server action, RLS and module enforcement.
- Branch A (internal attendance): attendance, payroll, tips, bar inventory, tasks, table allocation on. Branch B (external attendance): attendance, payroll, bar inventory, tasks on; tips off. Staff belong to A only.

Result: **1 passed** (final run). Teardown clean (organization, locations, users, sessions removed); ledger still 100.

## NOT TESTED on DEV (reported, not fabricated)

- **Confirmed payments / overpaid period.** Confirmed payments can never be deleted (even by an organization delete), so a disposable fixture cannot contain one without permanent residue. Netting of confirmed payments, and an overpaid period never offsetting another, are proven by the unit suites (`payroll-balances.test.ts`, `dashboard-readers.test.ts`, `dashboard-model.test.ts`).
- **External (Neon) attendance with real clock data.** DEV has no external clock and the Neon connection is blanked for tests; the Unavailable behavior is what is verified.
- **Native (internal-attendance) payroll.** Unavailable by design on the Dashboard (documented limit); not part of the figure.
- **WebKit / tablet viewport on real data.** The demo Playwright already runs host-tablet and server-mobile for the Dashboard; the real-data pass used Chromium desktop and phone.

## Findings

No blocking defect; no application code changed. Notes:

1. The existing self-service Payroll tab is visible to staff (their own pay only). The Dashboard does not link to it for staff by design; no other person's data appeared in it.
2. DEV already holds about thirty older synthetic `v2h-*` harness organizations from earlier suites. One more (`v2h-3e34ec40` and `v2ho-3e34ec40`: five payroll periods, three payments of which two are confirmed, three users) was left by this pass's first failed attempt, before confirmed payments were removed from the fixture. Confirmed payments cannot be deleted, so it was left in place rather than bypassing the immutability trigger. It is synthetic and harmless.
3. Fixture traps: changing a user's password ends the harness JWT session (Bar Inventory's live-session check then refuses), and the app's slug login can divert into universal-PIN enrollment on a PIN collision, so the spec signs in with a session cookie instead.
