GO means _no technical release blocker was found_. It does **not** authorize a Production migration, a Recipe import, a Bar Inventory data injection, a `development → main` merge or a deployment. Owner approval and a same-day Production preflight remain required.

## 1. Executive decision

- **No release blocker** (per the definition: unauthorized access, data corruption, broken core CRUD/archive/image access, organization isolation, migration inconsistency, unsafe/destructive import, secrets, lost update) was found.
- **Two items need work during preflight, neither blocks entering it:**
  1. The import tool **refuses Production by design** (`--target` accepts only `local` or `dev`). A Production import needs a separately reviewed, owner-approved change to the tool. (§10, P-3)

- **One Low defect** was reproduced: the validator inside `bar_recipe_category_reorder` never rejects an unknown ID (§5, F-1). Authorized managers only, tenant-scoped, display-order only. Recommended fix before the Production migration batch, owner's call.
- No application source, schema, policy, Storage, DEV, PROD or `main` change was made by this audit.

## 5. Authorization / RLS (Area C)

Layered design, verified in the SQL (`20261028140623`, `20261028193159`):

- **Reads:** all six tables have RLS on, `anon`/`public` revoked, `authenticated` has `SELECT` only. Policies require an **active membership** in the row's organization (`private.recipes_is_member`) and, for archived rows, management (`recipes_is_manager`: owner / general_manager / shift_manager). Child tables inherit via `recipes_can_read_variant → recipes_can_read_recipe`.
- **Writes:** no `INSERT/UPDATE/DELETE` grant and no write policy on any table. Every write is a `SECURITY DEFINER` RPC (`bar_recipe_save`, `_set_archived`, `_set_image`, `_category_save/_set_active/_reorder`) whose first act is `private.recipes_begin(p_org)`: `auth.uid()` not null **and** active management membership in the supplied organization. A client-supplied organization ID is therefore re-validated against the caller's own memberships; it is never trusted.
- **Search path:** every `SECURITY DEFINER` function sets `search_path = ''` (pgTAP "security definer helpers pin search path", "RC-136").
- **Import RPC:** `bar_recipes_import` is revoked from `public/anon/authenticated`, granted to `service_role` only, and still requires an active management actor in the target organization.
- **Server-action layer** (defense in depth): organization derived from the signed-in user's membership via `getCurrentUser(slug)`, `requireLiveSession`, Staff short-circuited, zod validation. No Recipe code imports the admin client; the service role is used only by the import script.
- **Cross-tenant:** composite FKs `(id, organization_id)` make cross-organization parents impossible ("cross-tenant parent is rejected"); pgTAP covers foreign manager, inactive manager/member, Staff, anon.
- **Org-creator bypass (#106)** concerns `private.has_org_role`; Recipes do not use it.

**F-1 (Low, reproduced) — `bar_recipe_category_reorder` ID validation is vacuous.** In
`exists(select 1 from unnest(p_ordered_ids) id where not exists(select 1 from public.bar_recipe_categories c where c.id=id and …))` the unqualified `id` binds to `c.id`, so the inner predicate is always true and unknown/foreign IDs are never rejected. Reproduced on a throwaway PostgreSQL 16 (deleted afterwards): `bogus_id_detected = f`. Bounded impact: caller must be an active manager; the count and distinctness checks still apply; the `UPDATE` is restricted to `organization_id = p_organization_id`, so nothing outside the tenant can change; the UI only submits the org's own IDs. Worst case is a crafted request leaving some `display_order` values unchanged (ties/gaps). Not covered by pgTAP (only complete-list success and fallback-included denial are). **Classification: Low — SHOULD FIX BEFORE RELEASE (owner decision).** Because the 7 migrations ship to PROD together, correcting it in a new pre-release migration (qualify the alias, add a foreign-ID pgTAP case) is cheaper than a post-release migration. It is not a blocker.

## 7. Concurrency / versioning (Area D)

`bar_recipe_save` (update), `_set_archived`, `_set_image` and the category RPCs lock the organization (`pg_advisory_xact_lock`) then the row (`FOR UPDATE`), then compare `p_expected_version` with the locked row; a mismatch raises `PT409` with the current version and last editor. The whole save (recipe, variants, ingredients, steps, garnishes) is one statement-level transaction; `unique_violation` is translated inside the same function whose subtransaction has already rolled back child writes. pgTAP: "stale version fails", "stale leaves all rows, children and version unchanged", category stale, stale image. App: `recipeWriteError` maps `PT409 → stale` with reload/keep-editing recovery (editor tests). The editor loader refuses to pair old fields with a newer version ("Recipe changed while loading"). No lost-update path found. Creation has no version (new row) and is protected by the unique constraints.

## 8. Archive / restore (Area E)

Archive keeps the row (number stays reserved); restore requires an active category (replacement offered); editing or image change on an archived recipe is rejected; Staff lose read access to archived recipes and their images (RLS + storage policy + action filter); management retains read. Direct URL for Staff resolves to unavailable (action filters `is_active`, RLS enforces). Covered by pgTAP 0044/0045, hosted real suites and `recipes-management` e2e. TC-19 (manual Staff run) is **not** needed for this to be technically established (§12).

## 9. Images / Storage (Area F)

Bucket `recipe-images`: `public = false`, 2 MiB limit, MIME allowlist `image/webp`, `image/jpeg`. Exactly three `storage.objects` policies (select/insert/delete); **no UPDATE policy**, objects are immutable (new UUID path per upload). Object names must match `<org-uuid>/<recipe-uuid>/<uuid>[-thumb].(webp|jpg)`; `recipes_image_parts` returns NULL on any other shape (no cast errors), and read/write helpers additionally require the recipe row to exist in that organization. Reads: active member of the org and recipe readable (archived → management only). Writes/deletes: active management of the org and the recipe **active**. The DB rejects `image_path` outside the recipe's own folder (`bar_recipes_image_scope`), the RPC validates paired paths/version, and no client can write `image_path` directly. Access is via signed URLs (TTL 3600 s, batch-signed thumbnails, refreshed before expiry, retry once, placeholder). Replacement: upload new pair → set metadata under version lock → remove old; failure paths compensate and warn; pgTAP 0045 (33) and the hosted suite report zero orphan objects. Residual: a failed compensating delete can orphan an object (logged, bounded by 2 MiB cap; B-RC-5 repair script is a backlog item). Server-action body limit is 8 MB (`next.config.ts`), above the ≤ 2 MiB + 300 KiB stored pair; Vercel's request cap (≈4.5 MB) also clears it. Nothing public, nothing cross-organization.
