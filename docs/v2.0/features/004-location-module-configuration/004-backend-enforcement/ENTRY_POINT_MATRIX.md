## 5. Storage, jobs, Realtime, background

- **Storage:** recipe images use an organization-scoped path; no location. Server guard (`recipe-image-actions`) only; storage-level location enforcement belongs to V2-005.
- **Jobs / schedulers:** there are **no** `pg_cron` or JWT-less jobs. Task recurrence, checklist generation and notification / opening-reminder sweeps are lazy RPCs invoked by a signed-in user and already pass through `tasks_begin`, so a Disabled location generates nothing.
- **Realtime:** respects RLS; the restrictive SELECT policies therefore also hide Disabled-location rows from Realtime subscribers (pgTAP 0038 still passes in staged mode).
- **Service role:** unchanged. The admin client is used only by the exempt auth routes; service-role tooling bypasses RLS by design and is not reachable from the browser.
- **Exports:** inventory export is a Server Action (`exportDataAction`) behind the `bar_inventory` guard; payroll statement/ledger reads are Server Actions behind `payroll`.

## 6. V2-005 gaps recorded (not hidden)

1. Organization-level tables above cannot carry a location-scoped DB check until V2-005 adds location binding. A signed-in, authorized user who bypasses Server Actions and calls PostgREST directly can still reach **payroll, recipes, team (memberships/profiles), attendance links and availability/time-off** data they are already authorized to access at the organization level; the module toggle does not restrict that path.
2. Server Actions that take no location from the request resolve it from the persisted active context (`getPrimaryLocation`). For org-wide data (e.g. schedule reads) the guard answers "is the module on at the location you are operating?", matching navigation (V2-004.003) — not "is it on at every location".
3. `task_notifications_mark_read` (the caller's own read-state) is unguarded at the DB.
