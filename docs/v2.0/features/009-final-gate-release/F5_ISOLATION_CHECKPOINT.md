## Confirmed authorization gap

The Stage B fix deactivates one organization's membership and credential, then avoids an account-wide ban if another active organization membership or Overall role exists. Its reactivation path still calls `updateUserById(profileId, { ban_duration: "none" })` unconditionally. An independent global ban is therefore cleared by a manager acting only in organization A. A new test starts with an independent `24h` ban and another active membership; it fails because the code clears the ban. A second new test confirms that deactivating the only active membership replaces an independent `24h` ban with a 100-year ban. Eight existing focused tests pass.

There is no persisted ban owner or provenance in the current model. Checking only the count of active memberships cannot determine whether a pre-existing ban was created by this organization's deactivation, by another organization when it was the last active membership, or by an independent administrator. A conditional skip for multi-organization users would address the reproduced case, but not the single-organization version while preserving Feature 017's reactivation contract. Deactivation can also overwrite an independent ban's duration when no other access remains. A complete correction needs an approved account-wide ban ownership rule and likely a provenance mechanism; this checkpoint does not choose one.

The two membership writes are best-effort, not atomic with Auth. A membership created in another organization between the access lookup and Auth update could still be affected by an account-wide ban. This is a concurrency risk, not a reproduced exploit in this checkpoint.

### Proposed forward migration — **design only; not created or applied**

1. Add one authenticated, transaction-scoped `public.team_set_member_active(p_organization_id uuid, p_target_profile_id uuid, p_active boolean, p_reason text)` RPC. It must run as `SECURITY DEFINER` with fixed empty `search_path`, qualified object names, immediate `REVOKE ALL` from `PUBLIC` and `anon`, and `GRANT EXECUTE` only to `authenticated`. No new exposed table or table RLS policy is needed; the existing tables keep RLS enabled, and this definer function must enforce its own complete actor/target checks. Revoke the current table-level `UPDATE` on `public.memberships` from `authenticated`, then grant only column-level `UPDATE (roles)` so an authenticated client cannot bypass the transactional active-state path. Preserve the existing role-change RLS policy and other table grants; verify its callers before migration. `passcode_credentials` remains service-role-only outside the definer function. Existing `(organization_id, profile_id)` unique indexes on memberships and credentials and the Auth user primary key serve the lookups. Add indexes only if measured query plans require them.
2. Inside the RPC, verify `auth.uid()` and a live `auth.sessions` `session_id`; reject a banned actor. Load the actor's **active membership** in the supplied organization and enforce the existing owner/general-manager hierarchy, target-role restriction, self-target ban, reason length, and requested current state. Never authorize through a slug, request metadata, organization creator bypass or user-editable claims. The route retains its present validation and maps explicit RPC outcomes to the existing HTTP statuses.
3. Lock the target `auth.users` row, actor membership and target membership/credential rows in a fixed order, then check `banned_until` under that lock. The target Auth-row lock serializes a concurrent GoTrue ban write with this transition; no cross-organization membership-count lookup or global ban write remains. On reactivation, any active or unreadable Auth ban rejects the whole transaction before membership or credential becomes active. This includes unknown legacy bans. On deactivation, preserve any Auth ban without modifying its duration. Update membership and credential together; insert the audit event in the same transaction. Missing credential, read failure, write failure or audit failure rolls everything back. A repeat request returns an explicit already-in-state result without an Auth write or second audit event.

Test two organizations, single-organization lockout/reactivation, independent and unknown bans, inactive memberships, the owner/GM hierarchy, self-target and unauthenticated denial, failed writes/audit, repeated calls, opposing/concurrent transitions, and denial of a direct `memberships.active` update by `authenticated`. 5. Roll out the migration before the route switches to the RPC. Rollback of application code must **disable Team (de)activation** or use a forward fix; it must never restore the vulnerable account-wide ban writes. Keep the RPC until no deployed client calls it, then revoke/drop in a later migration. No Auth ban backfill or automatic unban is allowed. A separate global-admin recovery decision is needed for legacy unknown bans.

This design needs explicit owner approval for a forward migration and for replacing the old GoTrue session kill with organization-scoped enforcement. It is not permission to create the migration.
