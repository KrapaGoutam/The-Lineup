## 2. Review of the proposal — what changes

**Kept:** one authenticated `SECURITY DEFINER` RPC, fixed empty `search_path`, atomic membership+credential+audit, no Auth ban writes, rollout migration-first, revoke direct `memberships.active` writes, owner-approved global-ban separation.

**A1 — Reactivation does NOT read or gate on the Auth ban (replaces checkpoint step 3).** The proposal rejected reactivation whenever `auth.users.banned_until` is active or unreadable and locked the `auth.users` row. Replace with: the RPC never makes a decision from Auth state and never writes Auth. It returns `auth_restricted` (plain, non-locking read of `banned_until`) as **advisory output only**. Reasons: (1) Cases A–D then stay independent by construction (A: membership active + global ban → GoTrue still blocks sign-in/refresh/`getUser` and live-session helpers; B: inactive + no ban → locator lookup and RLS block; C: reactivate under an independent ban → ban untouched, still blocked; D: global admin lifts the ban → org state unchanged). (2) A lock on `auth.users` cannot make PostgreSQL+GoTrue atomic: a ban written one millisecond after commit is equally valid, so the lock buys a false guarantee while adding GoTrue lock contention and Auth-schema coupling. (3) Rejecting would strand every member deactivated by Feature 017 (which wrote a 876000h ban) with no tool for a global administrator to clear it, and make a manager's action depend on state they cannot see. (4) Residual exposure accepted: a globally banned person with an unexpired token and a membership re-activated in A can read A through RLS in modules whose helper does not require a live session — identical to their exposure before the deactivation (D-11/H-S1), not created by F-5.

**A2 — A missing credential row is tolerated; a failed write is not.** The proposal rolled back when the credential row is missing. With 45 credential-less active DEV members that would make Team (de)activation unusable for them, and reactivation would deadlock (the reset route requires an active member). F-5C is fixed by single-transaction atomicity, not by treating "no row" as an error. Update the credential with `GET DIAGNOSTICS row_count`; 0 rows is reported (`credential_present:false`); any SQL error aborts everything. Invariant after success: credential row (when present) `active = membership.active`.

**A3 — Lock actor and target membership rows together, ordered by `profile_id`, then re-check authority.** One statement: `select … from public.memberships where organization_id = $1 and profile_id in (actor, target) order by profile_id for update` (LockRows sits above Sort, so lock order = sort order → no deadlock). After the lock, evaluate actor `active`/roles from the locked (re-evaluated) rows. This closes: two owners deactivating each other concurrently (second sees an inactive actor → denied; with organization-scoped actors at least one active owner remains; an Overall owner can still deactivate the last organization owner by design), deactivation racing reactivation, and a manager acting on a stale role. The credential row is locked by its own `UPDATE`. Contention is trivial at this scale.

**A4 — Strict live session.** New `private.team_live_session()` (same body as the other helpers) but **a JWT with no `session_id` is denied** (Tasks/Tips contract), because this is a privileged administrative write. Also denies a globally banned actor. It does not widen D-11.

**A5 — Authority equals the existing RLS policy, evaluated server-side, denial before disclosure.** From `auth.uid()` only (never a slug, header, metadata or claim role): Overall owner → any target; Overall manager → target without owner/general_manager; active org owner → any target; active org general_manager → target without owner/general_manager. Everything else (shift_manager, host, server, location-only roles, Overall assistant_manager, assistant manager) is denied. Self-target denied for every role. Return one uniform `42501` for "no authority / org not found" **before** revealing whether the target exists; only an authorized actor may receive `P0002` (not a member). The route's `getCurrentUser(slug)` still supplies slug→org and the 401 `sessionInvalid` response, so route-level authority is **not** widened (an Overall-only admin still cannot use this route).

**A6 — Privilege change.** `revoke update on public.memberships from authenticated; grant update (roles) on public.memberships to authenticated;` Verified need: the only authenticated-client membership update is the designation change (`team-actions.ts:100`, `roles`). `insert`, `delete` and `select` grants and all four RLS policies are untouched. Codex must grep all tests/fixtures for authenticated-role updates of `memberships.active` and fix them to use the RPC or `postgres`.

**A7 — App wiring.** Route calls the RPC with the **user's cookie-bound client** (`createClient`), not `createAdminClient` (service role has `auth.uid() = null` → denied). Delete `hasOtherAccess`, every `updateUserById`, `PERMANENT_BAN_DURATION`, and the route-level `audit_events` insert (the RPC audits). Map: `already_in_state`→409, `28000`→401 `sessionInvalid`, `42501`→403, `P0002`→404, `22023`→400, anything else→500 with no detail.

**A8 — Idempotency means convergence, not "state already equal".** Old best-effort writes can leave membership and credential divergent. Return `already_in_state` (no write, no audit) only when the membership **and** the credential (if present) both already match; otherwise perform the missing writes and audit them as a normal change.

**A9 — Stale premise corrected.** The checkpoint's "documented creator bypass" item is already closed; it needs no review in F-5.

## 3. Migration specification (design only)

- **File/version:** `supabase/migrations/20261113110000_team_set_member_active.sql`. It sorts after the live Hosted DEV ledger head (`20261113100000`) and **before** the shelved `20261113120000_v2008_track2_backfill_executor.sql`, so the shelved executor never becomes out-of-order. Never reuse, cherry-pick or merge the executor. Confirm the version is unused on `development` before committing. Forward-only, one `begin … commit`.
- **Objects:**
  1. `private.team_live_session() returns boolean` — `stable`, `security definer`, `set search_path = ''`; banned-user check; **requires** a `session_id` claim that matches a live `auth.sessions` row (`not_after` null or in the future). `revoke all … from public, anon, authenticated` (called only from the definer).
  2. `public.team_set_member_active(p_organization_id uuid, p_target_profile_id uuid, p_active boolean, p_reason text) returns jsonb` — `security definer`, `set search_path = ''`, every object schema-qualified. `revoke all … from public, anon, service_role; grant execute … to authenticated;` verify the final ACL in pgTAP (Supabase default privileges also grant `service_role`).
  3. Privilege change from A6.
- **Body order:** null `auth.uid()`→`28000`; `team_live_session()`; validate args (`p_active` not null; `btrim(p_reason)` 3–500 → `22023`); resolve actor authority **without target info** (Overall roles + actor membership; lock per A3 needs the target id, which is a request parameter, not a disclosure); lock rows (A3); authority + hierarchy (A5) → uniform `42501`; target row absent → `P0002`; convergence check (A8) → `already_in_state`; credential `UPDATE` (A2); membership `UPDATE` with `row_count = 1` assertion (`raise` otherwise); audit insert; return jsonb `{outcome:'changed'|'already_in_state', membership_active, credential_present, auth_restricted}` where `auth_restricted` = `coalesce(banned_until > now(), false)` from a non-locking read (reactivation only; absent Auth row → treat as error).
- **Audit row:** `action` `member_deactivated` / `member_reactivated` (unchanged names), `entity_type 'membership'`, `entity_id` target uuid text, `reason`, `before_state {active, credential_active}`, `after_state {active, credential_present, auth_restricted}`, `actor_profile_id = auth.uid()`. Same transaction → failure rolls everything back.
- **Not touched:** `auth.users`, GoTrue, `passcode_credentials.locator/synthetic_email`, passwords, `location_memberships` (rows retained for history; inert without an active org membership), any RLS policy, any other function, any backfill, no automatic unban. No new table, index, or policy (existing unique `(organization_id, profile_id)` indexes serve every lookup).
- **Rollback / forward fix:** never restore the account-wide ban writes. To disable, ship a forward migration that revokes `execute` (or makes the function raise) and temporarily returns the route to 503; re-granting `update` on `memberships` is a separate, explicit forward decision (restores only the pre-F-5 org-scoped RLS-bounded path). Keep the RPC until no deployed client calls it.
- **Compatibility:** no data migration; legacy single-org users keep the exact guarantee that the membership and credential rows lock them out; existing legacy 876000h bans stay in force (R-4).

## 4. Session revocation without a global ban

An already authenticated person loses organization A when `memberships.active` becomes false, because every authority path re-reads it per request:

- RLS via `private.has_org_role` (requires `active`); `getCurrentUser`, `getEntryUser`, the context resolver and org readers read memberships with `active = true` under the user's own RLS (their own inactive row is invisible); `postgres_changes` re-evaluates RLS per delivered change; every `*_live_session`-gated predicate (Tasks, Tips, Schedule, Payroll, Inventory, Attendance, Kiosk) is combined with an active-membership clause (kiosk's gap was F-1, fixed in 89). The same token still works for B because B's membership is active.
- **Findings (none blocks F-5):**
  - **R-1 (P3, UX):** `requireLiveSession` only calls `auth.getUser()`; it used to flag org deactivation through the ban (`sessionInvalid:true`). Now a deactivated user's Server Action gets an RLS denial or a silent 0-row update, not a clean sign-out. Authorization is intact. Routes using `getCurrentUser` already return 401 `sessionInvalid`. Record for B3 gateway; add one test that pins "authority is denied", not the UX.
  - **R-2 (P3, defense in depth):** `public.payroll_location_authorized` has an `or lm.active` branch with no org-membership check. Not a bypass today (`getPayrollActor` resolves the context and `getEntryUser` first, and the function returns only a boolean), but it breaks the "location rows never confer authority without an active org membership" invariant. Do **not** fix in F-5; add to the D-11/B3 list and pin current behaviour in the new pgTAP.
  - **R-3 (by design, non-guarantee):** an Overall owner/manager is unaffected by organization deactivation. Organization restriction cannot revoke global authority.
  - **R-4:** previously deactivated members carry a 876000h ban. Under A1 they can be reactivated at the organization level but cannot sign in until a global administrator lifts the ban; the UI must show the `auth_restricted` warning. Before rollout, an authorized session must count these (M-1: inactive memberships whose `auth.users.banned_until > now()`), read-only.
  - **R-5:** because of F-6, a person cannot currently hold a working credential in two organizations. F-5's multi-org protection matters for service-provisioned multi-org memberships and for B3; the account-wide ban hazard (locking B because A deactivated) is real today for those rows.
  - **R-6:** an org owner/GM can `DELETE`+`INSERT` a membership directly to re-create it; org-scoped, no cross-org effect, not widened. Out of scope.

## 6. F-6 compatibility

The RPC is keyed by `(organization_id, profile_id)`, touches no locator, synthetic email, password or Auth row, and makes `memberships.active` the single authorization source. B3's person-based credentials therefore only need to replace one statement (the credential `UPDATE`) in a forward migration. F-5 adds no organization/password coupling, preserves existing credentials, and creates no B3 rollback hazard. **F-6 stays OPEN**: F-5 does not fix duplicate synthetic email, per-organization password derivation or PIN collisions, and must not be reported as doing so. B3 still owns PIN collisions, identity resolution, rate limits, legacy credential migration and role alignment (legacy `owner|manager|server` vs Overall / organization / location layers; no role rewritten in F-5).

## 7. Owner packet

**A. Architecture.** Organization (de)activation becomes one transactional database function. It changes only the organization's membership and credential, audits the change, and never writes or clears an Auth ban.

**B. Guarantees / non-guarantees.** Guarantees: a manager cannot affect another organization or a global ban; the pair never ends half-changed; a deactivated person loses that organization immediately on their current token while keeping others; two organization-level actors cannot leave the organization without an active owner by acting on each other. Non-guarantees: Overall roles are not revoked and an Overall owner may deactivate a last organization owner; a legacy or independent global ban is neither created nor lifted here; the old "session is killed" sign-out behaviour for single-organization deactivation is replaced by authorization denial; F-6, F-1, F-2, D-11, V9-T are not fixed.

**C. Database.** One private helper, one public RPC, one privilege change (direct `memberships.active` writes removed from `authenticated`). No table, policy, index, backfill.

**D–F.** See §4, §3 and §5.

**G.** Legacy single-org users stay locked out by membership+credential; multi-org users are no longer collaterally locked; B3 swaps one statement.

**H. Risks.** Direct `UPDATE` revocation can break an undiscovered caller (mitigated by repository grep and tests; rollback is a forward grant); legacy bans make reactivated people unable to sign in until a global admin acts (visible warning + M-1 count); R-1 UX; Hosted DEV/PROD require the migration before the route ships.

**I. Alternatives.** (1) Reject reactivation under any Auth ban with an `auth.users` row lock (Codex's original): rejected, see A1. (2) Keep the account-wide ban with a provenance table: rejected, a new table plus cross-service two-phase writes with no atomicity and larger scope; reconsider only if immediate GoTrue token invalidation per organization is mandatory.

**J. Decisions that need the owner (product policy only).**

1. **Q1 — Reactivation under a global ban (recommended: allow and show a warning).** Alternative: block until a global administrator lifts the ban.
2. **Q2 — May Overall owner/manager use the Team RPC (recommended: yes, mirroring the RLS policy they already have)?** The Team route itself stays organization-membership-only; V9-T is untouched.
3. **Q3 — Accept replacing the GoTrue session kill with organization-scoped authorization denial for single-organization deactivation (recommended: yes).**
4. **Q4 — Who lifts a legacy 876000h ban and by what process?** (No tool exists; needs a named owner, not a code decision.)

Everything else (locking, grants, error codes, idempotency, tests) is a technical acceptance criterion above, not an owner choice.
