## 1. Role models compared

| Model                        | Where                                     | Values                                                                                        | Notes                                                                                                                              |
| ---------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Legacy / org role            | `public.memberships.roles` (`app_role[]`) | `owner`, `general_manager`, `shift_manager`, `host`, `server`                                 | Array type, but **DEV has only single-element arrays** (59 rows). It is a tier ladder; it does not say host and server must differ.                      |

Key facts about "what a user can do today" (from function bodies, single-active-location org with **no** location rows, i.e. the legacy-fallback state):

- **DB:** org owner/GM have manager-level access in Schedule, Attendance, Payroll, Inventory and Recipes regardless of location rows. `shift_manager` gets level 2 only while the org has ≤1 active location (and, for Tasks/Tips/Schedule/Board, no location rows). `host`/`server` get level 1 (floor/staff) under the same fallback.
- **TypeScript resolver:** `location:access` / `location:operate` require an **active location membership** (or an Overall role). There is **no legacy fallback in TS** (`location-access.ts`); org owner/GM get `org:admin` only when no location is requested. A member without a row resolves to `no_access` for operations (V2-003.001 EVIDENCE scenario 14; `fixes/dev-preview-login-location-access.md`: "a genuine member without an assignment stays denied by design").
- Therefore after the V2 app ships, **every real member with no location membership loses operational access until assigned**. The backfill is a hard release dependency, not a convenience.

## 2. Combine semantics that make mapping non-trivial

| Module group                       | Function(s)                                                           | Combine rule when both an org role and a location row exist                                                                                                                      |
| ---------------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tasks, Tips, Schedule              | `tasks_profile_level`, `tips_profile_level`, `schedule_profile_level` | `coalesce(location role level, org role level)` — **the location row overrides the org role**, so a lower location role **reduces** access (owner 4→staff 1).                    |
| Attendance, Payroll, Bar Inventory | `attendance_`/`payroll_`/`inventory_profile_level`                    | `greatest(location level, org level, overall level)` — a location row can only raise.                                                                                            |
| Table Allocation (floor board)     | `can_operate_board`                                                   | Overall, **or** org floor role **and** (active location row at the location, **or** the legacy single-location fallback).                                                        |
| Recipes, Inventory org-manager     | `recipes_is_manager`, `inventory_is_manager`                          | Org owner/GM (+ shift_manager for Recipes; + shift_manager at N≤1 for Inventory) **or an active `manager`/`assistant_manager` row at ANY location of the org** (org-wide spill). |
| Kiosk management                   | `kiosk_can_manage_location`                                           | Overall owner/manager, **or** org owner/GM, **or** active `manager` row at that location.                                                                                        |

Levels: staff 1, assistant 2, manager 3, owner 4. No authorization threshold above 2 was found (a manager check is `>= 2`; access is `> 0`), so owner(4) vs manager(3) is operationally equivalent today (pattern search, not exhaustive — Batch B re-confirms).

## 4. Authorization invariants and how the plan satisfies them

| Invariant (task §6.3)                               | Satisfied by                                                                                                                                                               |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No location staff gains organization administration | Org roles untouched; location rows grant no `org:admin`. Staff→`staff` only.                                                                                               |
| No cross-organization access                        | One org per transaction; manifest ids; location must belong to the org (checked); composite keys.                                                                          |
| No inactive membership becomes active               | Rows only for **active** members; existing inactive rows → abort, never reactivate.                                                                                        |
| No Overall Owner silently created                   | No write to `overall_roles` in any batch (count must remain 0 in postflight).                                                                                              |
| No missing assignment guessed                       | Multi-location orgs and ambiguous arrays are skipped; nothing inferred by name/order.                                                                                      |
| Highest-applicable-capability preserved (V2-D019)   | Mapping is the identity on the tier ladder. DB `greatest` modules unchanged. `coalesce` modules change level 4→3 (no consumer of 4 found).                                 |
| Employee PIN flows compatible                       | `passcode_credentials` are keyed (org, profile) and untouched. Login still succeeds; the backfill only restores post-login location access that the V2 app requires.       |
| Kiosk permissions remain location-scoped            | `kiosk_can_manage_location` unchanged; an org owner/GM mapped to `manager` keeps the same kiosk rights; assistant/staff gain none. (D7 adds a UI path only — see D7 plan.) |
