## 2. Exact vulnerable surface (deployed definitions, read from `pg_proc` / `pg_policies`)

### 2.1 Recipes (organization-scoped book; no `location_id` on any recipe table)

| Object                                                                                                                                                                     | Authorizer                                                          | What a location manager / assistant manager reaches                                       |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `bar_recipe_save`, `bar_recipe_set_archived`, `bar_recipe_set_image`, `bar_recipe_category_save`, `bar_recipe_category_set_active`, `bar_recipe_category_reorder` (6 RPCs) | `private.recipes_begin(org)` → `private.recipes_is_manager(org)`    | Create, edit, archive and re-categorize **every** recipe and category of the organization |
| Storage `recipe_images_insert`, `recipe_images_delete` (bucket `recipe-images`)                                                                                            | `private.recipes_can_write_image(name)` → `recipes_is_manager`      | Upload and delete recipe images org-wide                                                  |
| `bar_recipes` / `bar_recipe_categories` SELECT policies                                                                                                                    | `recipes_is_member(org) AND (is_active OR recipes_is_manager(org))` | Read archived / inactive rows (visibility, not management)                                |

`recipes_is_manager(org)` is true for: Overall owner/manager/**assistant_manager**; org `owner`/`general_manager`/**`shift_manager`**; or an active member holding an active `manager` **or `assistant_manager`** `location_memberships` row at **any** active location of the organization (`20261108160000_batch_b_inventory_recipes.sql:445-479`). `bar_recipes_import` is not client-executable.

### 2.2 Inventory (hybrid: catalog is organization-level, stock is location-level)

| Object                                                                                                                                                                                                                     | Authorizer                                                                                                                                                             | Effect                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **12 catalog writers:** `inventory_vendor_{create,update,set_active}`, `inventory_category_{create,update,set_active}`, `inventory_subcategory_{create,update,set_active}`, `inventory_product_{create,update,set_active}` | `private.inventory_begin(org, **location**)` → `inventory_can_access_location` → **location-scoped level ≥ 2 at a location the caller chooses**                        | Create, rename, deactivate **shared** vendors, categories, subcategories and products that every location of the organization uses |
| Location writers (stock, bulk count, imports, order drafts, date lots, freshness, storage layout, saved views)                                                                                                             | same seam                                                                                                                                                              | Correct: these rows _are_ location-scoped                                                                                          |
| SELECT policies on `inventory_vendors/categories/subcategories/products` (+ `inventory_change_log` for org-level rows)                                                                                                     | `private.inventory_is_manager(org)` — Overall owner/manager/assistant, org owner/GM, shift manager at N≤1, or **any active location manager/assistant row in the org** | **Read** of the shared catalog. Documented as intended (SCOPE_AND_SECURITY §2.2); not treated as a vulnerability                   |

`private.inventory_is_manager` is **read-only** (used only by SELECT policies). The Inventory _write_ spill therefore comes from the 12 catalog RPCs using a location-scoped guard for organization-scoped rows — not from `inventory_is_manager`. (The earlier register entries H-6 and the B2 package name `inventory_is_manager`, which is the read tier; the write path is the location-scoped `inventory_begin` seam.)

### 2.3 Application layer

- Inventory: `runCatalogCommandAction` → `resolveManager` → `getInventoryActor` (location-scoped, active location) → `inventory_*` RPC. A location assistant manager is shown and can run the shared-catalog commands in the Bar Inventory UI (`src/features/bar-inventory/actions/inventory-actions.ts:408-437` `resolveManager`, `:529-583` `runCatalogCommandAction`). **The UI is not stricter than the database here.**
- Recipes: `actor.isManager` = effective tier ≥ assistant at the **active** location (`src/features/recipes/data/recipes-actor.ts:25-75`). The UI is the stricter side (V2-005 007-recipes EVIDENCE §4), but still grants editing to a location assistant manager at the active location.

### 2.4 Related observations (independent review, not part of the correction)

- Recipe **writes do not check the `recipes` module** at the database (`location_module_key` includes `recipes`, but only the import function references it); module gating for Recipes is action-layer only — the V2-005 007-recipes residual. Inventory writes do check their module inside `inventory_begin`. Decide separately whether that asymmetry is intended.
- An independent read-only review re-ran the probe and scanned every function in every schema for writes to the catalog and recipe tables: **no missed writers** (the only extras, `inventory_ensure_system_vendor` and `recipes_apply`, are private and not client-executable); clients hold no non-SELECT grants and no write policies on these tables.

## 3. Contract comparison — what the documents actually say

| Source                                       | Statement                                                                                                                                                                                                          | Reading                                                                                                                                       |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| ACCESS_MODEL §4.2, §5                        | A location role applies **at that location**; belonging to an organization does not grant other locations; assistant managers cannot alter manager designations or delete historical records.                      | Location roles are location-scoped. Silent on organization-level catalog management.                                                          |
| MODULE_SCOPE_MATRIX                          | Recipes `ORGANIZATION` ("shared across the organization by design"); Bar Inventory `HYBRID` ("Catalog (vendors, products) is Organization-level. | V2-005 Recipes PLAN §1.3                     | "Location Managers / Assistant Managers have management authority for recipes within their organization." pgTAP 0069 case 39 and 0070 RV-060 assert it; EVIDENCE §4 records the UI-stricter residual.              | **Documented and tested, but broader than the access model.** A deliberate V2-005 choice, never escalated as a decision against ACCESS_MODEL. |
| V2-005 Bar Inventory SCOPE_AND_SECURITY §2.2 | `inventory_is_manager` = "Catalog read tier". Silent on who may write the catalog.                                                                                                                                 | **Undecided, not decided.**                                                                                                                   |
| V1 history (`20261026170000`)                | `inventory_is_manager` = org `owner`/`general_manager`/`shift_manager`; `inventory_begin(org, location)` always passed for any active manager ("today every active manager works every location").                 | In V1 org scope == location scope. **Classification:** Inventory catalog writes = _design gap_ (undocumented regression of the V1 org-manager contract). Recipes writes = _documented but over-broad contract_ that conflicts with the least-privilege direction the owner stated for S1. The correction needs an explicit owner decision for each (D-10).

## 5. Current vs expected permission (proposed Option A — see §10)

Rule: **an organization-level capability authorizes organization-wide management; a location-level capability authorizes only operations scoped to that location.** To avoid a regression for single-location tenants (where the two scopes coincide), tier-2/location roles keep catalog management only while the organization has **at most one active location** — the same compatibility pattern `inventory_profile_level` already uses for `shift_manager`.

| Actor                                                                                           | Org-wide catalog management today     | Proposed (Option A)                                                         |
| ----------------------------------------------------------------------------------------------- | ------------------------------------- | --------------------------------------------------------------------------- |
| Overall owner / Overall manager                                                                 | ✅                                    | ✅ (unchanged)                                                              |
| Overall assistant manager                                                                       | ✅                                    | ✅ only if the org has ≤ 1 active location                                  |
| Org owner / general manager                                                                     | ✅                                    | ✅ (unchanged)                                                              |
| Org shift manager                                                                               | ✅ Recipes always; Inventory at N ≤ 1 | ✅ only if N ≤ 1 (aligns Recipes with ACCESS_MODEL §5.5 and with Inventory) |
| Location manager / assistant manager                                                            | ✅ at any N                           | ✅ only if N ≤ 1; **location-scoped operations unchanged at any N**         |
| Location staff, inactive, cross-org, cross-location without authority, no-row member, anonymous | ⛔                                    | ⛔ (unchanged)                                                              |

Reads (`recipes_is_member`, `inventory_is_manager` for SELECT, archived-recipe visibility) are **unchanged**: sharing the catalog with location managers is documented and intended.

## 6. Business behavior potentially affected

- **Pilot (single-location) tenants: no change** under Option A (verified for the D-2 ladder: zero capability delta at N=1 — [D-2 equivalence output](security-s1/d2_role_ladder_equivalence_output.md)).
- **Multi-location tenants** (e.g. a future two-location group): location managers and assistant managers stop maintaining the shared recipe book and the shared vendor/product list; the organization owner / general manager (or an Overall manager) does. They keep every location-scoped operation (counts, restocks, order drafts, freshness, storage layout, saved views) at their own location.
- **A tenant that opens its second location flips behavior** for its location managers and shift managers at that moment. This is intentional but surprising; the second-location creation flow should say so (UX, out of E-1 scope).
- Inventory **read** of the shared catalog by location managers/assistants is retained, so their screens keep working; only the management commands become unavailable.

## 7. Safe minimal correction (design only — not implemented)

**One forward-only migration after `20261112220000`**, no table or policy change, no data change:

1. New predicate `private.catalog_can_manage_org(p_org uuid)` — `SECURITY DEFINER`, `STABLE`, `search_path = ''`, live-session gated, true for Overall owner/manager; active org `owner`/`general_manager`; or, **only when the organization has ≤ 1 active location**, Overall assistant manager, org `shift_manager`, or an active `manager`/`assistant_manager` location row in that organization (active membership required). Revoked from `public`/`anon`; EXECUTE for `authenticated` only if any policy needs it (none planned).
2. Recipes: `recipes_begin(org)` and `recipes_can_write_image(name)` call the new predicate. **`recipes_is_manager` is left as is**, so archived/inactive _read_ visibility is untouched.
3. Inventory: each of the **12** catalog RPCs adds one guard after `inventory_begin(org, location)`: `if not private.catalog_can_manage_org(p_org) then raise exception … using errcode = '42501'`. The 12 definitions must be regenerated from the **deployed** bodies (`pg_get_functiondef`), not from historical migration text, with the signature, `SECURITY DEFINER`, `search_path = ''` and ACLs asserted unchanged.
4. Application: expose the new decision to the UI so it never offers an action the database refuses — a `public.catalog_authorized(p_organization_id)` RPC (same pattern as `recipes_org_authorized`), consumed by `getInventoryActor`/`resolveManager` (catalog commands only) and `recipes-actor.ts`. Location-scoped Inventory commands keep the existing actor path.

Alternatives considered: _edit `inventory_begin`_ (rejected — cannot distinguish catalog from stock RPCs); _add `location_id` to catalog tables_ (rejected — contradicts the matrix and is a data migration); _explicit per-user catalog capability table_ (cleaner long-term, rejected as not minimal: new table, policy and UI).

## 8. Forward compatibility

- **Ordering with B2 (role backfill):** the D-2 ladder adds _no_ capability at N=1. Once an organization has ≥ 2 locations, the only capability a D-2 row adds is for `shift_manager → assistant_manager` (org-wide catalog read + the E-1 write). The correction must therefore land **before** any multi-location backfill (D-2c) and before a second real location is created.
- **Module enforcement (V2-004.004):** unaffected; `assert_location_module_enabled` still runs inside `inventory_begin`. Recipes keep their existing `guardModule` at the action layer.
- **Overall Assistant Manager:** ACCESS_MODEL grants "assistant manager capabilities across all organizations". Option A treats organization-wide catalog management as a manager-tier capability (outside the N ≤ 1 compatibility rule). Owner to confirm (D-10b).
- **Future capability model:** if the owner later wants per-person catalog editors, the single predicate is the one seam to replace.
- **Generated types:** a new RPC changes `database.generated.ts`; splice by hand (the CLI also emits two unrelated drifts — see the B1 note).

### 13.3 Behaviour change to communicate

In an organization with **two or more active locations**, location managers and assistant managers (and the organization shift manager) can no longer create, edit or archive recipes, recipe categories, recipe images, vendors, categories, subcategories or products; the organization owner / general manager (or an Overall role) does. They keep every location-scoped operation. A tenant that opens its **second location flips behaviour at that moment**; the second-location creation flow should say so (UX, out of scope here).

### 13.4 Residual notes

- **Concurrency window:** the location count is read per statement under READ COMMITTED; a catalog write that races a second location's creation can commit under the old count. The write is not tenant-crossing and not wider than the previous behaviour, so no lock was added.
- Recipes writes still do not check the `recipes` **module** at the database (action layer only): unchanged V2-005 residual (§2.4).
- **Independent review (one read-only reviewer, whole package): no P0, no P1.** It confirmed the 12 regenerated bodies are byte-identical to migration history apart from the single call swap, found no unguarded writer in any schema, no non-SELECT grant or policy on the shared tables, no UPDATE policy on the `recipe-images` bucket, and that single-location organizations are unchanged. The 1 → 2 location race was analysed as serializable-consistent (one RPC statement wide) and accepted without a lock. Findings in the tooling and UI were fixed or mitigated — see [HANDOFF.md](HANDOFF.md).
